Chapter 1

The big picture

An inference server has one job: turn many people's prompts into streamed answers, as fast and as cheaply as the hardware allows. Almost everything MiniServe does follows from two facts about how a GPU runs a language model.

Fact 1: each new token needs a full read of the weights

A model generates text one token at a time. To produce each token, the GPU runs the whole network once, which means reading every weight out of GPU memory. Qwen3-0.6B's weights are 1.19 GB computed in BF16. Your GPU moves 318.8 GB/s measured. So a single step can never take less than

1.19 GB ÷ 318.8 GB/s = 3.73 ms

which caps one request at about 268 tokens per second, however clever the code. The surprise is what happens with more requests: the GPU reads those same 1.19 GB once per step and can apply them to 1 sequence or to 64. The arithmetic per weight is tiny either way. Serving many requests in the same step is nearly free. That is why batching is the heart of every inference engine.

Fact 2: every token you keep costs memory

To avoid recomputing the past, the model stores each token's keys and values (the KV cache). For Qwen3-0.6B that is

2 × 28 layers × 8 heads × 128 dims × 2 bytes = 112 KiB per token

On a 6 GB card that also holds Windows, the CUDA runtime, the weights and some working memory, MiniServe's start-up profiling found room for 17,120 tokens of KV cache measured. A single 4,096-token request needs 448 MiB. Memory, not compute, decides how many requests fit at once.

What MiniServe is, in one paragraph

MiniServe is a small LLM inference server written in Python and PyTorch. It serves Qwen3-0.6B on an RTX 3060 Laptop GPU through an OpenAI-compatible streaming API, and implements the core ideas of production engines such as vLLM: continuous batching, a paged KV cache with preemption, prefix caching, chunked prefill, speculative decoding (n-gram drafts with an exact rejection sampler) and INT8 weight quantization. Every feature can be switched off, so its effect can be measured against a naive Hugging Face baseline that serves one request at a time.

Common mistake

"A faster GPU (more TFLOPs) makes chat faster." For decoding, the limit is memory bandwidth, not arithmetic. An RTX 3060 can do far more math per step than decoding needs; it spends the step waiting for weights to arrive.

Check yourself

Why is adding a second request to a decode step almost free?

Each step has to read all 1.19 GB of weights anyway. A second sequence reuses the same weights already being streamed through the GPU and adds only a little arithmetic plus its own KV reads. The step time barely grows while the tokens produced double.

Where does "112 KiB per token" come from?

K and V (2) × 28 layers × 8 KV heads × 128 dimensions per head × 2 bytes per BF16 value = 114,688 bytes = 112 KiB.

If decode is so cheap per extra request, what stops us from batching 1,000 requests?

Memory. Each request's KV cache grows by 112 KiB per token, and only 17,120 tokens fit on this GPU. Eventually compute would also become the limit, but on a small GPU memory runs out first.

Chapter 2

How an LLM writes text

A language model never writes a sentence. It outputs one score for every word piece it knows, something picks one, and the whole thing runs again. Everything about serving follows from that loop.

Tokens and logits

A tokenizer turns text into integer token IDs. Qwen3 knows 151,936 of them. "Hello world" might be [9707, 1879]; an emoji can be several tokens. The model takes the IDs and returns logits: one score per vocabulary entry, for the next position. A sampler turns those 151,936 scores into a single token, the token is appended, and the model runs again.

Sampling: greedy, temperature, top-k, top-p

  • Greedy (temperature 0): take the highest score. Deterministic. Benchmarks use it.
  • Temperature T: divide every logit by T before softmax. T < 1 sharpens the distribution toward the top token; T > 1 flattens it.
  • Top-k: keep only the k highest-scoring tokens.
  • Top-p (nucleus): keep the smallest set of tokens whose probabilities add up to at least p. With a confident model that might be 2 tokens; with an unsure one, 200.

In the code

MiniServe samples a whole batch with one trick, the exponential race: draw E ~ Exp(1) for every vocabulary entry and take argmax(p / E). That is an exact sample from p (it is the Gumbel-max trick in disguise), it runs as a single batched GPU operation, and a per-request random generator makes seeded requests reproducible no matter what else shares the batch.

src/miniserve/runner/sampler.py

def sample(logits, params, generators):
    greedy_tokens = logits.argmax(dim=-1)
    if all(p.greedy for p in params):
        return greedy_tokens                      # fast path: benchmarks are greedy
    probs = compute_probs(logits, params)         # temperature, then top-k / top-p
    noise = exponential_noise(probs.shape, generators, logits.device)
    sampled = (probs / noise).argmax(dim=-1)      # exact sample from probs
    return torch.where(is_greedy, greedy_tokens, sampled)
Common mistake

"Top-p 0.9 keeps the tokens whose probability is above 0.9." No: it keeps the most likely tokens until their total reaches 0.9. Also, the sampler sees probabilities only for the last position of each sequence: computing logits for every prompt token would waste 622 MB for a 2,048-token prompt computed (2,048 × 151,936 × 2 bytes).

Check yourself

What does temperature 0.5 do to logits of 4.0 and 2.0?

They become 8.0 and 4.0. The gap doubles, so after softmax the top token's share grows: from about 88% to about 98% for this pair. Lower temperature, sharper distribution.

Why can't the 128 output tokens of one request be computed in one forward pass?

Token 2 depends on token 1, which only exists after the model has run and the sampler picked it. Generation is autoregressive. (Speculative decoding, Chapter 10, works around this by guessing tokens and checking them in one pass.)

Why does MiniServe only compute logits for the last token of each sequence?

Only the last position's logits pick the next token. Logits for all prompt positions would cost memory (151,936 values each) and time for nothing. The runner gathers the hidden states of the last positions first, then applies the LM head.

RMSNorm, in float32

x / rms(x) × weight, where rms is the root of the mean of the squares. MiniServe computes it in float32 and multiplies by the weight after converting back to BF16, the same order as Hugging Face. Change the order and the logits drift slightly.

Grouped-query attention (GQA)

Qwen3 has 16 query heads but only 8 key/value heads: each KV head is shared by 2 query heads. Keys and values are what the KV cache stores, so GQA halves the KV cache (112 KiB per token instead of 224) and halves the KV bytes read per decode step.

QK-norm

Qwen3 applies an RMSNorm to every query head and every key head before rotating them. Qwen2 didn't. Forget it and the model still runs and still produces fluent-looking text, just wrong text. The float64 comparison test in Chapter 16 exists to catch exactly this kind of bug.

RoPE: position by rotation

Attention by itself has no idea of order. RoPE rotates each query and key by an angle that grows with the token's position, so the dot product between a query and a key depends on how far apart they are. Qwen pairs dimension i with dimension i + 64 (the "rotate half" layout). Every token is rotated by its own position in its own sequence, which is why the engine passes a positions tensor instead of assuming 0, 1, 2, …

SwiGLU MLP and the tied LM head

The MLP is down(silu(gate(x)) × up(x)). At the end, a final RMSNorm and a matrix multiply with the embedding matrix give the logits. Qwen3-0.6B's checkpoint still ships a separate lm_head.weight; MiniServe's loader never reads it, saving 311 MB computed (151,936 × 1,024 × 2 bytes) of a 6 GB GPU.

Why fuse matrices?

At load time MiniServe stacks q_proj, k_proj and v_proj into one qkv_proj, and gate_proj with up_proj into gate_up_proj. Same math, but one matrix multiply instead of three (or two). Each GPU kernel launch costs about 28 µs on this WSL2 setup measured, and Chapter 17 shows that launches, not math, dominate a step. Fewer, bigger kernels are almost always better.

return self.o_proj(out.reshape(t, self.q_size))

Check yourself

How much KV memory per token would Qwen3-0.6B need without GQA?

Twice as much: 16 KV heads instead of 8, so 224 KiB per token instead of 112 KiB, and half as many tokens would fit in the same pool.

Why does every token in a batch need its own position value?

RoPE rotates by the token's position within its own sequence. In a flattened batch, token 3 of the flat tensor might be position 412 of request A while token 4 is position 0 of request B.

What symptom would you expect if QK-norm were missing?

No crash and plausible-looking but wrong text. That's why correctness is checked against Hugging Face's logits rather than by eyeballing outputs.

Prefill, decode, and memory speed

Arithmetic intensity

A GPU has two speed limits: how many floating-point operations per second it can do (FLOP/s), and how many bytes per second it can read from memory. Arithmetic intensity is FLOPs done per byte read. Below a certain intensity the GPU waits for data (memory-bound); above it, it waits for math (compute-bound).

In a decode step with B sequences, each 2-byte weight is read once and used in 2·B FLOPs (a multiply and an add per sequence). Intensity ≈ B FLOPs per byte. A consumer Ampere GPU needs very roughly 60 to 150 FLOPs per byte before compute becomes the limit estimate. So at B = 1, 8 or even 32, a decode step is far on the memory-bound side: adding sequences costs almost nothing extra.

The speed limit of a decode step

If decode is memory-bound, a step can't finish faster than the time to read everything it needs:

step ≥ (weight bytes + KV bytes read) ÷ bandwidth

Attention is the exception to "batching is free": each sequence reads its own KV cache, so KV bytes grow with batch size × context length. Long contexts make attention the dominant cost.

Common mistake

Timing GPU code without torch.cuda.synchronize(). Kernel launches return immediately; without a sync you measure how fast Python queued the work, not how long the GPU took. MiniServe's step ends with one .tolist() on the sampled tokens, which syncs, so per-step wall time is honest.

Check yourself

Why is prefill compute-bound and decode memory-bound when they run the same weights?

Prefill multiplies each weight by hundreds of prompt tokens at once (high intensity, big matmuls). Decode multiplies each weight by one token per sequence: 2 FLOPs per 2 bytes per sequence, so intensity is about the batch size, far below the ridge.

At batch 32 and 512 tokens of context, roughly how many bytes does one decode step read?

Weights 1.19 GB plus KV 32 × 512 × 112 KiB ≈ 1.88 GB, so about 3.07 GB, a floor of about 9.6 ms at 318.8 GB/s.

Why doesn't batching help attention the way it helps the linear layers?

Weights are shared by every sequence, so one read serves all of them. Each sequence's keys and values are its own; nothing is shared, so attention reads grow with every sequence and every token of context.

Chapter 5

The KV cache

Without a cache, the model would redo the whole conversation for every new token. With one, each step computes keys and values for the new token only, and the cache becomes the single biggest consumer of memory you have to manage.

The problem it solves

Attention for the newest token needs the keys and values of every earlier token, at every layer. Recomputing them each step means token n costs work proportional to n, so a whole answer costs work proportional to n². But a token's keys and values never change once computed (they depend only on the tokens before it). So compute them once, keep them, and each step only adds one new row per layer.

In MiniServe

Why zeros instead of torch.empty?

Masked-out slots still get multiplied by an attention weight of 0. Uninitialized GPU memory can contain bit patterns that mean NaN, and 0 × NaN = NaN. Zeroing 1.9 GB once at start-up costs milliseconds and removes a whole class of heisenbugs.

Common mistake

"The KV cache stores the earlier tokens." It stores, for every layer, each token's key and value vectors (after the projections, QK-norm and RoPE). That's why it's 28 × larger than a single embedding, and why a block can only be reused if every token before it is identical (Chapter 9).

Check yourself

A 2,048-token request: how much KV memory, and what fraction of the 17,120-token pool?

2,048 × 112 KiB = 224 MiB, about 12% of the pool. Eight such requests would need 16,384 tokens: almost the whole pool.

Why is it safe to keep a token's K and V forever once computed?

In a causal (decoder-only) model a token only attends to earlier tokens, so its keys and values depend only on the prefix up to it. Later tokens never change them.

What would happen to the pool if Qwen3 used 16 KV heads instead of 8?

224 KiB per token, so the same 1,872 MiB holds 8,560 tokens: half as many concurrent requests.

Chapter 6

The 6 GB budget

Where does a 6 GB GPU's memory actually go? MiniServe answers that at start-up, the way vLLM does, by measuring, and gives the KV cache whatever is left.

The profiling recipe

  1. Load the weights. Record allocated memory (1,141 MiB).
  2. Run a dummy prefill at the full token budget (2,047 tokens) and a dummy decode with 64 sequences, sampled with top-k/top-p. Record the peak (weights + 488 MiB of activations).
  3. Free everything temporary, ask the driver what's in use now (2,554 MiB, including other apps).
  4. KV pool = total × utilization − in use − peak activations = 6,144 × 0.80 − 2,554 − 488 ≈ 1,872 MiB = 1,070 blocks of 16 tokens.

Without step 2 the engine would size the pool from free memory at idle, run its first big step, and crash with "CUDA out of memory" exactly when traffic arrives.

free, total = torch.cuda.mem_get_info()

Common mistake

Setting utilization to 0.95 "to fit more". On a laptop that also drives Windows, other apps grow; when they do, the next allocation fails mid-request. The 20% headroom is insurance, and the startup log tells you exactly what it costs.

Check yourself

Why run a dummy decode step as well as a dummy prefill during profiling?

They peak in different places: prefill on big MLP activations, decode on gathering many sequences' keys/values and on sampling 64 rows of logits. Profiling only one would undersize the reserve for the other.

Where would most of the extra memory go if you switched to INT8 weights?

To the KV pool: about 425 MiB more, roughly 3,900 more tokens, so more concurrent requests. That is the main reason to quantize on a small GPU.

Name four things besides the KV cache that take GPU memory here.

Other apps (Windows), the CUDA context and PyTorch runtime, the model weights, and peak activations (including logits and the sampler's sort).

Chapter 7

Continuous batching

Batching shares each weight read across many requests. The hard part is that requests arrive at random times and finish at random lengths. Continuous batching re-decides who is in the batch at every single step.

  • Explain how a "flat batch" lets sequences of different lengths share one forward pass.
  • Walk through MiniServe's scheduler: token budget, order, admission.

Three ways to batch

  • Static batching (what model.generate() on a padded batch does): collect a batch, pad everyone to the longest prompt, run until every sequence is done. A 5-token answer waits for a 500-token one; a new request waits for the whole batch.
  • Dynamic batching: collect requests for a few milliseconds, then run them as a static batch. Helps with arrivals, not with the finishing problem.
  • Continuous batching (also called iteration-level scheduling, from the Orca paper, OSDI 2022): the scheduler decides membership at every decoding step. A finished sequence leaves immediately; a new one takes its place at the next step. No slot sits idle waiting for the slowest request.

The flat batch

How can sequences with different lengths, some prefilling and some decoding, share one forward pass without padding? Look back at Figure 3.1: every operation except attention treats each token independently. So the engine concatenates all of this step's tokens into one long "super-sequence" and runs the linear layers, norms and MLP on it once. Only attention needs to know where each sequence starts and ends, and it gets that from metadata.

MiniServe's scheduler

There is no "prefill phase" and "decode phase". Each step has a token budget (max_num_batched_tokens, default 2,048), and each sequence simply needs its next N tokens computed: N = 1 for a decode, N = the rest of the prompt for a new request. The rules:

  1. Running sequences first, oldest first. Each gets the tokens it needs (usually 1), so ongoing streams never stall behind new arrivals.
  2. Then waiting requests, first come first served, while budget, memory and max_num_seqs (64) allow.
  3. A sequence that just finished frees its memory in the same step; the next step can admit someone new.

    if not bm.can_allocate(cached, ...): break      # no memory: wait

    out.scheduled.append(ScheduledSeq(seq, num_new)); budget -= num_new

Common mistake

"Continuous batching just means bigger batches." The batch size is capped the same way in both schemes; the difference is when membership changes. Static batching changes it per batch, continuous per step. And no padding: sequences of any length share a step through the flat batch.

Check yourself

Why are running sequences scheduled before waiting ones?

Their users are mid-stream and notice every pause (inter-token latency). A waiting request hasn't started yet. Serving running sequences first also keeps their 1-token decodes from being crowded out by big prefills.

Why can't attention be computed on the flat batch like the other layers?

Attention mixes tokens: each query must only see keys from its own sequence and only earlier positions. Every other layer works token by token, so it doesn't care which sequence a row belongs to.

In Figure 7.1, why do only 3 of the 7 rows produce logits?

Only the last token of each sequence picks a next token. C's first four rows are prompt tokens whose outputs are only needed for their keys and values.

Chapter 8

Paged KV cache & preemption

Batching only helps if requests fit in memory together. The classic way to store KV caches wastes most of that memory; PagedAttention borrowed the fix from operating systems: virtual memory with fixed-size pages.

  • Compute a token's slot from its position and the block table.
  • Explain recompute preemption and why the newest request is evicted.

The problem: reserving for the worst case

Before PagedAttention (vLLM's SOSP 2023 paper), servers reserved one contiguous slot per request, sized for the longest possible output. Most answers are short, so most of each slot was never written. The paper found earlier systems wasting most of their KV memory to over-reservation and fragmentation, and reported 2–4× higher throughput from fixing it.

On your GPU: a 17,120-token pool with fixed 4,096-token slots holds 4 requests. The same pool, handed out 16 tokens at a time, holds 44 of the benchmark's 384-token requests computed.

The fix: blocks and block tables

  • KV memory is split into fixed-size blocks of 16 tokens (vLLM's default). 1,070 of them on this GPU.
  • Each sequence has a block table: logical block i lives in physical block block_table[i], exactly like an OS page table.
  • Blocks come from a free list only when the sequence needs them, and go back the moment it finishes.
  • Waste: at most one partly filled block per sequence (under 16 tokens).

Slot mapping: where does token p go?

slot = block_table[p // 16] × 16 + p % 16

Example: sequence A's token at position 37 is in logical block 37 // 16 = 2 at offset 37 % 16 = 5. A's block table says logical block 2 is physical block 4, so the slot is 4 × 16 + 5 = 69. Every step, the runner computes one slot per new token (the slot_mapping tensor) and writes keys and values there.

When memory runs out: preemption

Paging lets the scheduler admit requests optimistically, so sometimes a running sequence needs a new block and none is free. MiniServe then preempts the newest running sequence: frees all its blocks, puts it back at the front of the waiting queue, and later prefills its prompt plus everything it already generated again. Its output so far is kept; the client only sees a pause. This is recompute preemption, what vLLM's V1 engine does. The alternative, swapping the blocks to CPU memory and back, costs PCIe transfers and bookkeeping (vLLM V0).

Why evict the newest?

It has done the least work, so recomputing it is cheapest, and evicting it keeps first-come-first-served fairness: older requests keep making progress. MiniServe also refuses to admit new requests in a step that had to preempt, since memory is already short.

src/miniserve/engine/scheduler.py · making room

while not bm.can_append(seq, num_new):

    self._preempt(victim)                # free its blocks, num_computed = 0, front of waiting
    if victim is seq:
        break                            # it had to evict itself: nothing newer was left

How attention reads a paged cache

The block table is also how attention finds a sequence's keys. MiniServe has no custom kernel yet, so for each step it turns the block tables into the slot of every context position (a vectorized page-table lookup) and gathers those keys into a contiguous tensor:

src/miniserve/attention/backends.py

def context_slots(block_tables, length, block_size):
    pos = torch.arange(length, device=block_tables.device)
    return block_tables[..., pos // block_size] * block_size + pos % block_size

kg = k_cache[g.ctx_slots]                # gather: [batch, context, kv_heads, dim]

That gather is an extra copy of every key and value each step. A paged-attention kernel (FlashAttention's paged mode, or a Triton kernel you could write) reads the blocks in place. That's one of the clearest next steps (Chapter 18).

Common mistake

"Paging makes attention faster." It doesn't; if anything, indirection costs a little. Paging makes memory use efficient, so many more requests fit at once, and that is what raises throughput.

What are the costs of a bigger block size, like 256?

More waste per sequence (up to 255 unused token slots), coarser prefix sharing; in exchange, smaller block tables and more efficient kernel reads. FlashAttention-2's paged mode requires multiples of 256.

A preempted request had generated 40 tokens. What happens to them?

They stay in its token_ids. When it's readmitted, the prompt plus those 40 tokens are prefilled again (possibly partly from the prefix cache), and generation continues from token 41. The client sees a pause, not a restart.

Chapter 9

Prefix caching & chunked prefill

Two scheduling ideas that fall out naturally once memory is paged and steps have a token budget: reuse the KV blocks of prompts that start the same way, and split long prompts so they don't freeze everyone else.

  • Explain ref counts and the LRU list of cached blocks.
  • State the chunked-prefill trade-off between TTFT and inter-token latency.

Prefix caching

Many requests start with the same tokens: a system prompt, few-shot examples, earlier turns of a chat. Their KV blocks are identical, so compute them once and share. MiniServe follows vLLM:

  1. Only full blocks are cached. Each gets a hash of (previous block's hash, its 16 tokens).
  2. A new request walks its prompt block by block, looking each hash up; it reuses every match (incrementing the block's ref count) and stops at the first miss.
  3. The last prompt token is never matched: it must go through the model to produce logits.
  4. When a cached block's ref count drops to 0 it is not erased: it moves to an LRU list and is only overwritten when memory is needed. A finished conversation's blocks stay reusable for the next turn.

Chunked prefill

A 2,000-token prompt arrives while 30 sequences are decoding. Prefill it in one step and that step takes much longer, so all 30 streams stall at once: a spike in inter-token latency. With a token budget the fix is almost free: decodes go first (1 token each), and the long prompt gets whatever budget is left this step, the rest next step (the Sarathi-Serve idea, OSDI 2024).

Common mistake

"Prefix caching caches responses." It caches the keys and values of prompt blocks; the response is still generated. And it matches only identical token prefixes at the same positions, never "similar" prompts.

Check yourself

Why include the previous block's hash in each block's hash?

A block's keys and values depend on every token before it. Chaining makes a hash identify the whole prefix, so a hit guarantees the cached KV is exactly what we would have computed.

A 40-token prompt with block size 16 is sent twice. How many tokens does the second request compute?

Blocks 0 and 1 (tokens 0–31) are full and cached; the last 8 tokens are a partial block, never cached. So 32 tokens are reused and 8 are computed.

What does chunked prefill trade away for smoother streams?

The long prompt's own time to first token (it takes several steps) and a little prefill efficiency (smaller matmuls, repeated attention reads of the earlier chunks).

Chapter 10

Speculative decoding

If a decode step is limited by reading the weights, then checking 5 tokens costs about the same as producing 1. So guess several tokens cheaply, and let the big model verify all of them in a single pass, without changing the output distribution at all.

After this chapter you can

  • Walk through draft, verify, accept and reject, with the exact acceptance rule.
  • Prove in one line why the output distribution is unchanged.
  • Compute expected tokens per step, and say when speculation stops helping.

The algorithm

  1. A cheap draft proposes k tokens d1…dk, with draft probabilities q.
  2. The target model runs once over [last token, d1, …, dk] and gets its own distribution p at every position.
  3. For i = 1…k: accept di with probability min(1, p(di) / q(di)). At the first rejection, sample a replacement from normalize(max(0, p − q)) and stop.
  4. If all k are accepted, sample one bonus token from p at position k+1.

With greedy decoding it reduces to: accept drafts while each equals the target's argmax; at the first mismatch, emit the target's argmax instead.

Why the output is exact (the one-line proof)

The chance of emitting token x at a position is: (draft proposes x and it's accepted) + (rejection, then the residual picks x) = q(x)·min(1, p(x)/q(x)) + P(reject)·(p(x) − min(p(x), q(x))) / P(reject) = min(p(x), q(x)) + p(x) − min(p(x), q(x)) = p(x). Here P(reject) = 1 − Σy min(p(y), q(y)), which is exactly the residual's total mass, so they cancel. MiniServe's chi-square test checks this with 200,000 samples.

How much does it buy?

If each draft is accepted with probability α, the expected tokens per target pass with k drafts is (1 − αk+1) / (1 − α).

Common mistake

"Speculation always helps." It helps when the GPU has idle capacity, which means small batches. At large batch sizes every step is already doing useful work for many sequences, and verifying extra guesses costs real time. Acceptance also matters: n-gram drafts are excellent when the answer copies the prompt and nearly useless for open-ended chat. Report it at concurrency 1, 4 and 16, including where it hurts. MiniServe's speculation is implemented and tested for exactness; its speed-up hasn't been measured yet.

Check yourself

With an n-gram proposer (a deterministic guess), what is the acceptance rule?

q is one-hot on the guessed token, so min(1, p(d)/q(d)) = p(d): accept with probability p(d). On rejection, sample from p with d removed (renormalized).

α = 0.8, k = 4: expected tokens per target pass?

(1 − 0.85) / (1 − 0.8) = (1 − 0.328) / 0.2 ≈ 3.36.

Why don't rejected drafts' keys and values need to be erased?

The engine only trusts slots below num_computed, which is advanced by the accepted count. Later steps write their own keys into those slots before anything reads them.

Per-row absmax INT8, by hand

For each output row r of a weight matrix: scale s = max|wr| / 127, stored values q = round(w / s), clamped to [−127, 127]. At run time, w ≈ q × s.

Row [0.40, −1.27, 0.031, 0.90]: max is 1.27, so s = 0.01. Stored: [40, −127, 3, 90]. Reconstructed: [0.40, −1.27, 0.03, 0.90]. The small weight lost precision (0.031 → 0.03), and one large outlier in a row would make s big and wash out every small weight in it. That's the problem LLM.int8(), GPTQ and AWQ attack.

src/miniserve/quant/int8.py

scale = w.abs().amax(dim=1).clamp(min=1e-8) / 127.0          # one scale per output row
qweight = torch.round(w / scale[:, None]).clamp(-127, 127).to(torch.int8)

def forward(self, x):
    w = self.qweight.to(x.dtype) * self.scale.unsqueeze(1)    # rebuild BF16 matrix (naive!)
    return F.linear(x, w)
Why the naive version is slow

Decode is limited by bytes moved. Plain BF16 reads 2 bytes per weight. The naive INT8 forward reads 1 byte, writes a 2-byte BF16 copy, then reads that copy again: about 5 bytes of traffic per weight instead of 2. It saves memory and costs speed. A fused kernel reads the int8 values and dequantizes them in registers inside the matmul, so it moves 1 byte per weight: that's where the decode speed-up comes from.

The landscape, for interviews

  • Weight-only (W8A16, W4A16): smaller weights, BF16 math. Best for memory-bound decode.
  • W8A8: weights and activations in INT8, uses INT8 tensor cores (Ampere has them), needs calibration.
  • FP8 needs Ada or Hopper tensor cores (RTX 40-series, H100). Your Ampere RTX 3060 can't compute in FP8.
  • LLM.int8() keeps outlier features in FP16; GPTQ and AWQ are calibration-based 4-bit methods.
  • KV-cache quantization (INT8 keys and values with per-token scales) would double the tokens in the pool: a strong level-up for a small GPU.

Always measure quality next to speed: perplexity on a fixed text, and how often greedy outputs agree with BF16. MiniServe keeps the embedding (which is also the LM head) in BF16, because quantizing it costs the most quality.

Common mistake

Reporting "INT8 is 2× faster" from the bytes alone. Measure it. With the naive kernel MiniServe expects INT8 to be slower per step and better only in KV capacity. Its INT8 path is implemented and loads; the memory, speed and quality numbers are still to be measured (Chapter 18).

Why would weight-only INT4 speed up decode but not prefill?

Decode is memory-bound, so a quarter of the bytes is a big win (with a fused kernel). Prefill is compute-bound: the math still happens in BF16, so fewer weight bytes barely matter.

What's the main benefit of INT8 weights for MiniServe on 6 GB, even with the slow kernel?

About 426 MiB more for the KV cache, roughly 3,900 more tokens, so more concurrent requests before preemption.

The protocol

MiniServe implements the subset of the OpenAI API that clients and benchmarks use: POST /v1/completions, POST /v1/chat/completions, GET /v1/models, plus /health, /metrics and /stats. With "stream": true the response is Server-Sent Events:

data: {"id":"cmpl-1","object":"text_completion","choices":[{"index":0,"text":" Ottawa","finish_reason":null}]}

data: {"id":"cmpl-1","object":"text_completion","choices":[{"index":0,"text":".","finish_reason":"stop"}]}

data: {"id":"cmpl-1","choices":[],"usage":{"prompt_tokens":6,"completion_tokens":2,"total_tokens":8}}

data: [DONE]

SSE rather than WebSockets: it's one-way (server to client), plain HTTP, works through proxies, and it's what OpenAI uses. MiniServe writes these bytes itself with a StreamingResponse, because helpers that add keep-alive comment lines break clients (vLLM's benchmark among them) that parse every data: line as JSON.

Two threads, two kinds of queue

The HTTP server runs on an asyncio event loop. The engine loop is blocking GPU work; run it on the event loop and every connection freezes during every step. So the engine runs in its own thread.

Measured: the price of sharing one Python process

Both threads need Python's GIL, and the engine holds it while launching kernels. At 4 concurrent requests, MiniServe made 63.5 tok/s through HTTP against 117.6 tok/s inside the engine alone measured. vLLM runs its engine in a separate process (talking over ZeroMQ) for exactly this reason. That's a planned level-up.

Incremental detokenization

A token isn't always valid text. In Qwen's byte-level vocabulary, "🚀" is three tokens, and each alone decodes to the replacement character "�". Stream token by token and the user sees garbage. MiniServe decodes a small sliding window and only emits text once it no longer ends in "�" (the algorithm vLLM and TGI use).

Stop strings, cancellation, backpressure

  • Stop strings are checked on text, not tokens (a stop string can span tokens). While stop strings are set, MiniServe holds back the last few characters that could be the start of one, so no part of a stop string is ever streamed.
  • Cancellation: when a client disconnects, Starlette cancels the streaming generator; MiniServe's finally calls engine.abort(request_id), which frees the KV blocks. Forgetting this is a classic leak: dead clients hold memory until the pool is full. The API test hangs up mid-stream and checks every block comes back.
  • Backpressure: if the waiting queue already holds max_waiting requests, new ones get HTTP 503 at once instead of joining a queue whose latency grows without limit.
  • Qwen3 thinking mode: the chat template can emit <think>…</think> reasoning; the chat endpoint passes enable_thinking=False.

Check yourself

Why can't the engine loop simply be an async function on the event loop?

Each step is blocking work: launching hundreds of kernels and waiting for the GPU. While it runs, the event loop can't accept connections or send anyone's tokens. A background thread (or process) keeps the HTTP side responsive.

What breaks if a disconnected client's request isn't aborted?

The engine keeps generating for nobody and the request keeps its KV blocks until max_tokens. Enough of them and the pool fills, causing preemption and stalls for real users.

Why is a 503 better than accepting every request under overload?

Past capacity, a queue only grows, and every queued request's latency grows with it. Rejecting fast lets clients retry or go elsewhere, and keeps latency bounded for the requests already accepted.

Rules for numbers you can defend

  • Percentiles, not averages. P50 is the typical user, P99 the unlucky one. With 200 requests a P99 rests on 2 data points; MiniServe uses 500 requests for every P99 it reports.
  • Closed vs open loop. Closed loop (N clients, each sends its next request when the last finishes) measures capacity. Open loop (Poisson arrivals at a set rate) shows queueing under real traffic. A closed loop can hide queueing delay: the load generator slows down exactly when the server does (coordinated omission).
  • Little's law as a sanity check: concurrency ≈ request throughput × mean latency. If your numbers break it, something is wrong with the measurement.
  • Same client, same prompts, fixed lengths. Seeded prompts sent as token ids (exact input length) and ignore_eos (exact output length), so every system does the same work.
  • Warm-up, one server at a time, watch the laptop. Warm-up requests aren't measured; nothing else runs on the GPU; nvidia-smi logs clocks and temperature so thermal throttling shows up.

A run finishes 500 requests in 200 s with mean latency 6 s. What concurrency was it?

Throughput 2.5 req/s × 6 s ≈ 15 requests in flight on average: about 16 clients, minus short gaps between requests.

Why is ITL different from TPOT?

TPOT is a per-request average. ITL pools every individual gap, so it shows stalls: one 500 ms freeze hidden inside an average TPOT of 45 ms shows up clearly in ITL P99.

A chunk can carry several tokens (an emoji completed by its third token arrives as one chunk), and some tokens produce no text at all (end of sequence). The server's token count is exact.

Architecture & a request's journey

One request, step by step

  1. POST /v1/completions arrives with "stream": true. completions() in api/server.py checks n == 1 and that prompt + max_tokens fits in max_model_len (else 400), tokenizes, checks the waiting queue (else 503), and makes an id like cmpl-….
  2. AsyncEngine.generate() registers an asyncio.Queue for the id and puts ("add", …) into the inbox.
  3. The engine thread drains the inbox: LLMEngine.add_request() wraps the prompt in a Sequence (WAITING) and appends it to scheduler.waiting.
  4. Next step, Scheduler.schedule() serves the running sequences, then looks at the waiting queue: find_cached_prefix() finds shared blocks, can_allocate() checks room, allocate() hands out blocks, and the sequence becomes RUNNING with all (or a chunk) of its prompt scheduled.
  5. ModelRunner.prepare() flattens every scheduled sequence into one batch: token ids, positions, one slot per new token, and attention metadata built from the block tables.
  6. Qwen3ForCausalLM.forward() runs 28 layers. In each one, paged_attention() writes the new keys and values into their slots, then attends through the block tables.
  7. compute_logits() runs only on the last row of each sequence; sample() picks the tokens; one .tolist() copies them to the CPU (the step's only sync).
  8. Scheduler.update() advances num_computed, appends the token, checks EOS and max_tokens, registers newly full blocks in the prefix cache, and frees a finished sequence's blocks.
  9. The engine thread publishes a RequestOutput to the request's queue with call_soon_threadsafe.
  10. Back on the event loop, IncrementalDetokenizer.add() turns token ids into text, StopChecker checks stop strings, and an SSE chunk goes to the client.
  11. Steps 4–10 repeat, one token per step (or more, with speculation), interleaved with everyone else's tokens.
  12. On EOS or max_tokens: a final chunk with finish_reason, a usage chunk, data: [DONE]. If the client hangs up instead, the generator is cancelled and its finally calls engine.abort(), freeing the blocks.
Interview move

When asked "walk me through your system", draw Figure 14.1 first, then narrate steps 1–12 for one request, then say what changes with 64 requests: the same loop, but each step carries 64 sequences' tokens through one forward pass. Stop there and let them choose where to dig.

Check yourself

Where is the only GPU-to-CPU synchronization in a normal step, and why only one?

The .tolist() on the sampled token ids at the end of ModelRunner.execute(). Every sync stalls the CPU until the GPU catches up, which stops the CPU from queueing the next work; the scheduler needs the token values, so exactly one is unavoidable.

Which component would you change to add a second model replica, and which wouldn't change?

A router in front of the API servers (and a second engine process per GPU). Nothing inside the engine changes: the scheduler, block manager and runner are per-replica.

Module notes

engine/sequence.py

One class carries a request through the engine. The invariant to remember: work left = num_tokens − num_computed. A new request has its whole prompt left; a decoding request has exactly 1 (the token just sampled, whose keys aren't stored yet); a preempted request has num_computed = 0 again.

engine/block_manager.py

Three structures: ref_counts (how many sequences use each block), free_ids (a deque of blocks holding nothing useful) and, for the prefix cache, cached (hash → block) plus evictable (an OrderedDict used as an LRU list). check_invariants() asserts that every block is in exactly one state; the Hypothesis test calls it after every random operation.

runner/model_runner.py

prepare() is plain Python building lists (ids, positions, slots); then everything goes to the GPU in a few pinned, non-blocking copies. execute() runs the model, gathers only the rows that need logits, samples, and syncs once. profile_num_blocks() is Chapter 6's recipe.

attention/backends.py

Builds the attention metadata once per step (shared by all 28 layers) and runs two paths: short queries (decodes, speculative verifies) padded into batched groups, and prefill chunks one sequence at a time. The GQA trick is worth reading slowly:

A bug worth knowing: the hidden sync

An early version wrote the batched result back with out[idx] = og[valid], where valid was a boolean mask. Indexing with a boolean mask makes PyTorch ask the GPU how many entries are True: a CPU–GPU synchronization, inside every one of 28 layers, every step. The fix is a precomputed integer index (valid_rows). Rule of thumb: in a hot loop, avoid .item(), .tolist(), print(tensor), boolean-mask indexing and torch.tensor(data, device="cuda") from pageable memory.

model/loader.py

Builds the model on PyTorch's meta device (no memory, no random init), allocates real storage directly in BF16, then copies each checkpoint tensor into place, stacking q/k/v and gate/up into the fused matrices. It refuses to finish if any parameter wasn't loaded, so a renamed tensor fails loudly instead of leaving random weights.

api/server.py

Most of the file is the OpenAI response shapes. The part to understand is generate_text(): an async generator wrapped in aclosing(), so that stopping early (a stop string) or being cancelled (a disconnect) always runs the cleanup that aborts the request.

The tiny float64 model

CI has no GPU. A randomly initialized Qwen3 with 2 layers and hidden size 64, built from transformers' own config class, runs on a CPU in milliseconds and exercises every code path. MiniServe runs it in float64. Why? In BF16 on a GPU, a sequence's logits change slightly with the shape of the batch it's in, because different shapes add numbers in a different order and floating-point addition isn't associative. A near-tie between two tokens can flip. In float64 those differences are around 10−15, so "batched output == single output" can be tested for exact token equality.

Measured

60 CPU tests pass in about 10 seconds. On the GPU, our model picks the same next token as Hugging Face on 20/20 prompts (largest logit difference 0.45 in BF16); 11/20 greedy 48-token generations match exactly, and on average the first 35 tokens agree before a near-tie flips; and after 300 requests with random aborts, every KV block is free again.

Why float64 exactness and GPU match rates are both needed

The float64 tests prove the logic (scheduling, paging, caching, speculation) is exactly right. The GPU tests prove the real weights load correctly and that the BF16 numerics are in the expected range. Neither alone would be convincing.

Check yourself

Why does the paged-vs-full-reservation test also check free blocks at the end?

A leak doesn't change outputs right away. It only shows up after thousands of requests as shrinking capacity. Asserting the pool returns to its full size after every variant catches it immediately.

What would the chi-square test catch that the greedy equivalence test can't?

An error in the sampling branch of speculative decoding (wrong acceptance probability or wrong residual distribution). Greedy decoding never exercises that path; only the distribution of many samples reveals it.

Headline

Negative result, keep it: at one client the baseline is faster (24.5 vs 15.7 tok/s; TPOT 41 vs 57 ms). MiniServe's step is launch-bound (below) and its engine shares a process, and the GIL, with the HTTP server; Hugging Face's single-request loop has less per-step overhead. Batching is what wins, and it wins by a lot.

Throughput vs concurrency

Latency vs concurrency

How to read these curves

  • The baseline is flat. It serves one request at a time, so more clients only make the queue longer: throughput stays put and time to first token grows with the queue.
  • MiniServe's throughput climbs with concurrency until memory runs out: each step carries more sequences for nearly the same cost. Past the point where the KV pool is full, preemption kicks in and the gains flatten.
  • Fixed slots (the same engine reserving 4,096 tokens per request) can only hold 4 requests at once on this GPU, so it flattens almost immediately: that gap is what paging buys.
  • Latency is the price. Each step carries more work, so time per token rises with the batch. A real deployment picks the concurrency where P99 latency still meets its target.

Check yourself

Why does continuous batching help even when the engine is launch-bound rather than bandwidth-bound?

The number of kernel launches per step barely depends on the batch size. 64 sequences share one step's 1,700 launches just as they share one read of the weights.

What evidence would convince you a step is launch-bound and not GPU-bound?

"What surprised you?"

"How would you serve a 70B model to a million users?"

Tensor parallelism within a node (one all-reduce per layer, needs NVLink), pipeline parallelism across nodes if needed, quantization to cut memory, many replicas behind a router that sends shared prefixes to the replica that has them cached, disaggregated prefill and decode pools so long prompts don't stall decoding, autoscaling on queue depth, and SLO-based admission control (goodput, not raw throughput).

"Why recompute instead of swapping to CPU memory?"

Swapping needs PCIe transfers both ways and bookkeeping for CPU blocks; recompute is simple and stateless, and for short sequences re-running the prefill is often cheaper than moving the blocks. The prefix cache can even make recompute nearly free if the evicted blocks haven't been reused yet. vLLM's V1 engine made the same choice.

"How do you know there are no memory leaks?"

Three layers: check_invariants() asserts every block is in exactly one state and ref counts match the block tables; a Hypothesis test runs hundreds of random operation sequences against it; and both the CPU equivalence tests and a 300-request GPU test with random aborts assert the pool returns to full. The API test also hangs up mid-stream and checks the blocks come back.

"How do you know speculative decoding doesn't change the output?"

Greedy: an exact token-for-token test against decoding without speculation, in float64. Sampling: the rejection rule is provably exact (Chapter 10), and a chi-square test over 200,000 samples checks the implementation matches the target distribution.

Mixed quiz

Twelve questions from across the book, deliberately out of order. Answer each before opening it.

1. Your P99 TPOT doubled when you went from 16 to 64 clients. Bug or expected?

Expected, up to a point: each step carries 4× the sequences, so each step takes longer, and past the KV pool's capacity preemption adds pauses. Check the server's preemption counter before calling it a bug.

2. What does num_tokens − num_computed equal for a sequence that is decoding?

1: the token just sampled, whose keys and values haven't been computed and stored yet.

3. Why might INT8 weights make decode slower in MiniServe today?

The naive forward rebuilds a BF16 matrix every call, moving about 5 bytes per weight instead of 2. Only a fused kernel turns fewer bytes into speed.

4. Two prompts share their first 47 tokens (block size 16). How many tokens can the second one reuse?

32: two full matching blocks. The third block (tokens 32–47) contains token 47, which differs, so its hash differs.

5. Why is the engine in a separate thread from the HTTP server, and what does that cost?

The step loop blocks; on the event loop it would freeze every connection. The cost is GIL contention between the threads (63.5 vs 117.6 tok/s measured at concurrency 4). A separate process removes it.

6. With α = 0.6 and k = 2, expected tokens per target pass?

(1 − 0.63) / 0.4 = (1 − 0.216) / 0.4 = 1.96.

7. What two numbers explain almost everything in this book?

1.19 GB of weights read per decode step (3.73 ms at 318.8 GB/s), and 112 KiB of KV cache per token.

8. Why does the paged allocator never need a sequence's blocks to be contiguous?

The block table translates logical positions to physical slots, and attention reads through it. Contiguity was only needed when each sequence's cache was one array.

9. Why does MiniServe sample with argmax(p / E) instead of torch.multinomial?

It is an exact sample from p, runs as one batched operation for every request, and lets each seeded request use its own generator, so seeded outputs don't depend on what else is in the batch.

10. A benchmark reports TTFT P99 from 120 requests. What do you say?

That P99 rests on one or two requests. Report P50/P90, or run at least 500 requests.

11. Which test would catch a forgotten QK-norm, and which would not?

The float64 logit comparison against Hugging Face catches it immediately. The batched-vs-alone equivalence test would not: both sides would be equally wrong.

12. The profiler shows ~1,700 kernel launches per decode step. Name two ways to reduce their cost.

CUDA graphs (replay the whole step with one launch) and fusion (fewer, bigger kernels: fused RMSNorm, fused QKV, torch.compile on the elementwise parts). Running on native Linux also cuts the per-launch cost.
